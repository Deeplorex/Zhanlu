# 湛卢架构，一页看懂

## 结论

**分工合理，当前实现还不具备发布条件。** 不需要推倒重做，也不应把现在的本机演示直接打包成正式产品。桌面壳、阅读界面、文件处理引擎各做一件事，能让常用阅读保持轻快，并把转换与 AI 的重任务隔开。代价是安装打包、进程通信和安全边界必须认真做好。

## 用户打开一份 PDF 时发生什么

```text
用户点开 PDF
    ↓
Tauri 桌面壳：打开窗口、让用户授权文件、启动受控引擎
    ↓
React 界面 + PDF.js：显示页面、缩略图、搜索与标签
    ↓ 仅当拆分、合并、转换或 OCR 时
Python 引擎：处理文件，在后台写出新的结果
    ↓
本机文件 + SQLite：保存结果位置、最近文件和可恢复的任务
```

| 部分 | 可以把它理解为 | 为什么保留 |
| --- | --- | --- |
| Tauri | 门和窗户 | 管窗口、本机文件授权、打包和引擎启动。官方支持把外部程序作为 sidecar 随应用打包。 |
| React + PDF.js | 阅读桌面 | 管界面与 PDF 阅读；PDF.js 的解析核心可在 worker 中运行，重文档也不必全部堵住界面。 |
| Python sidecar | 文件加工间 | 拆分、合并、转换、OCR、AI 任务可复用现有库，出错时与阅读界面隔离。 |
| SQLite（目标） | 任务账本 | 记住文件、任务和结果，关闭或崩溃后可核对与恢复。 |
| 按需 AI 能力包 | 需要时再打开的工具箱 | 不把大模型重量放进每次打开 PDF 的基本路径。 |

## 当前最需要修的四处

1. **本机访问边界**：现在窗口打开的是本机 HTTP 地址，API 可按路径登记并读取文件，缺少请求身份验证；配置中 CSP 也为 `null`。正式版应让 Tauri 从打包资源加载界面，并只让经授权的界面调用带会话身份的本机引擎。Tauri 官方提示，用 localhost 提供应用页面有额外安全风险，默认自定义协议更合适。
2. **引擎打包**：现在桌面壳寻找仓库里的 `engine/.venv` 并扫描端口，干净电脑无法这样运行。正式版应打包指定 sidecar、由桌面壳启动并验证实例身份；不根据“端口能连通”就复用服务。
3. **任务恢复**：现在任务只在内存，最近文件写在 JSON。正式版需要可取消、可重试、重启后可核对的任务与文件记录。SQLite 是适合单机应用的选择；输出先写临时文件，校验后再登记为完成。
4. **轻量与离线 AI**：Tauri 本身不能保证整个产品轻量；Python 库、OCR 模型和大模型才决定安装包大小与内存。主程序应独立完成阅读、拆合和基础转换；OCR 与本地模型按需安装，但首版交付必须让用户在断网时实际使用它们。

## 不建议现在做的事

- 不为“统一技术栈”而把整个 Python 处理引擎重写成 Rust。先完成真实功能、打包、安全与性能验收，再依据安装大小和启动数据决定是否替换局部算法。
- 不拆成多个常驻服务。首版一个受控引擎 sidecar，加按需启动的 OCR/模型进程即可。
- 不把目录搬家当成架构完成。`engine/ → apps/engine/` 与 `web/ → apps/web/dist/` 只是归位；真正的发布门槛仍是文件授权、任务恢复、离线能力和端到端验收。

## 判断它是否真的“轻量、快速、本地”

在干净 Windows 电脑上断网安装并测量：启动到可操作的时间、打开 1000 页 PDF 的首屏时间、滚动与搜索响应、空闲内存、安装包大小；同时验证拆合、转换、OCR 和本地问答全链路。结果记录在[发布验收](../product/mvp-v1/acceptance.md)中。无法通过时，应明确是哪个部件造成开销，而不是凭“用了 Tauri”就宣称轻量。
